## The boundary we can and cannot defend

A SHA chain inside the editable run authenticates nothing against an editor who can reseal that chain. HMAC records inside the same editable directory also do not solve rollback if the editor can replace their signing key or replay an earlier signed head. A valid historical prefix is not proof it is the latest state.

The proposed authority is a distinct trusted component with a private random key and a monotonically advancing batch registry/head outside the run workspace. The workspace coeditor may rewrite/delete/restore every current state, event, elapsed value, public receipt and marker inside the run, while leaving the original immutable input anchors unchanged. The coeditor does not control the authority's code, its private key, its registry/database/head or the protected parent that classifies actual fixture work. Those are explicit trust assumptions, not properties conferred by a different filename or HMAC alone.

The initial candidate can demonstrate this model using a separately opened authored test authority in another temporary directory. It cannot enforce isolation against hostile Python running as the same OS user: 0600 protects against other users, not another process with the same credentials. Production requires a genuinely protected separate principal/service or equivalent owner-controlled key/monotonic storage. No such production deployment is implemented or claimed. A malicious host, stolen key, substituted authority/verifier/code, or coordinated rollback of the complete trusted key+registry+head is outside this local fixture model. Without an external/hardware monotonic witness, full trusted-store rollback cannot be cryptographically distinguished from the original earlier state. If independent review requires that stronger threat model, the local component remains BLOCKED.

The trusted authority must remain available to verify currentness. HMAC receipts are internal evidence, not public signatures or independently verifiable publication certificates. Keys never enter run files, Git, reports, logs or external services.

## Identity and bootstrap

Only an explicit authored-fixture bootstrap creates a new authority/batch. The trusted authority path is selected by the trusted test harness, outside the run; it cannot be chosen or overridden by editable runtime configuration. Bootstrap uses an exclusive new path and an absent run path, creates a new random key, authority ID, batch ID and run nonce, and binds exact runtime/spec/code/plan hashes plus the canonical run path. The trusted registry rejects duplicate design/run registration. A run genesis includes the authority/batch/nonce binding before any analysis work. Adoption or migration of an existing v1/v1.1/v1.2 run is refused; failed history cannot be reset by enrolling it as a new signed batch.

Opening is not bootstrapping. Missing key, registry/database, head, bootstrap identity or run binding refuses; no automatic key generation, replacement, fallback verifier or re-enrollment occurs. Deleting a run marker does not delete its trusted registration. Recreating a deleted authority alongside an existing run refuses. A new authority for a genuinely new absent run has new random identities; restoring an old run afterward fails its nonce/authority/head binding. Deleting both every trusted anchor and the entire run is outside recoverable historical proof; restored old evidence does not receive acceptance under a new nonce.

## What is authoritative

For each batch the trusted store retains sequence, predecessor/head digest, pending work identity, immutable bindings, cumulative known operation/result-byte reservations, terminal state and a permanent analysis barrier. Its authenticated transition records bind phase/query ID, sweep, exact kind/definition/input hashes, full reserved operations/bytes, status, protected-parent observed timing, result/proof hash or explicit unknown, prior and next mutable-state hashes, authority/batch/nonce and sequence. SUCCESS, FAILED and UNKNOWN are distinct authenticated terminal events. Catalog and mandatory phases receive the same terminal authority as selected queries.

A successful phase requires an artifact proof: catalog success binds the rederived exact compiled plan; mandatory success binds validated source/primitive/uncertainty/view hashes and its observed logical bound. A caller-written elapsed0 is not success evidence. The protected runner computes/validates these proofs and classifies success/failure. There is no public arbitrary-payload signing or `mark_success` endpoint that accepts editable run assertions. The first standalone authority candidate uses a simple authored byte-producing phase worker with an independently fixed expected byte hash; it tests the authority lifecycle, not full F mandatory arithmetic. Real F proof adapters remain a separately reviewed integration task.

FAILED/UNKNOWN, and an admitted pre-work refusal under the existing analysis contract, latch the permanent trusted barrier. No reset, deletion, alternate name, new signer or continuation-approval mechanism exists for that batch. Source acquisition/its separately reviewed N1 continuation policy is unchanged; this is the analysis batch authority only.

## Ordered writes and crashes

1. Before dispatch, lock the trusted batch, verify authority identity/current head and exact mutable projection, then atomically commit a full reservation and pending identity to the trusted store. The public reservation receipt is a projection, never the head authority.
2. Only the protected runner owning that pending work may execute the fixed worker. Concurrent/duplicate/different work cannot dispatch while pending. A child cannot receive the private signing key or writable authority handle.
3. The protected runner validates the success artifact or records FAILED. It atomically commits the trusted terminal record/head/barrier and known charges before treating a mutable checkpoint as accepted. SUCCESS cannot replace a retained FAILED/UNKNOWN terminal or grant a refund without its success proof.
4. Mirror the authenticated receipt and next state to the run, fsync, then verify current projection against the trusted head. A crash or disk failure between trusted commit and mutable write leaves an authority/run mismatch and refuses new work. Never regenerate a terminal SUCCESS from edited run files.
5. A pending reservation after process death blocks all later work. Explicit forensic recovery may atomically mark UNKNOWN with all full reservations retained; it never reexecutes/refunds. If terminal persistence itself fails, the earlier pending authority state remains a barrier. Trusted transaction failure must not yield an accepted unanchored mutable state.

Run deletion, rollback/truncation, replacement public receipts, renamed failed events, fabricated elapsed/proof, and transplant from another run/design/phase must fail against the trusted current head and bound work identity. A genuine earlier SUCCESS receipt cannot authorize a later different work item or supersede a later failure. The trusted database/key are not exported as a reproducibility shortcut.

## Methods and implementation gates

A new standalone AUTHORED component candidate may exercise the above trust boundary with a separate fixture authority and no source/model work. Its tests must cover positive success and subsequent work, real child failure/abrupt death, pending UNKNOWN recovery/full charges, coedited FAILED/UNKNOWN current+event+receipt histories with zero future dispatch, valid-success artifact tampering, cross-authority/batch/design/phase transplant, stale signed success replay, mutable rollback/truncation, marker loss, missing/corrupt authority key/store/head and rebootstrap refusal, concurrency and crash windows before/after trusted terminal commit.

Independent review must first decide whether this explicit trusted-authority boundary satisfies the requested coordinated-workspace-edit threat model. A passing component test cannot create that trust assumption. Only after methods acceptance and component review should a separately versioned F engine consume authority capabilities for every analysis transition and phase success proof. Until then no F ledger version is promoted or controller acceptance renewed. Keep API/model spend0 and actual approvals null throughout this stage.
