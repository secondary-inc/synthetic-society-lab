## Lifecycle and binding

The caller must explicitly open an existing `GlobalFixtureLedger`; this run entry point never creates or replenishes it. Every run/config binds its explicit directory, ledger identity, policy, script, job/input hashes, per-unit plans, implementation hashes and Python runtime. The current scope is the same exact engineering instrument, authored DEMO notices and fictional ID/party-only profiles. This does not replace the nationwide demographic population. Creating another fixture directory remains a test-only operation, not fixed production owner bootstrap or authority.

Each pre/post phase uses the exact frozen job, instrument, own baseline, exposure, sampling and request serialization. Planner rederivation checks byte/token/cost bounds before the journal starts. The journal records STARTED before the client atomically reserves the exact request globally, then performs its authored POST and same-generation statistics lookup. No real network transport or key is present. The client durably settles authoritative fixture billing and safe visible-answer metadata before the phase can complete.

A phase file stores the exact answer envelope, own receipt, run/unit/phase and message hash. The journal then commits the result and validity disposition. Only after both are durable does the global ledger validate that phase file and transition to PHASE_COMMITTED, releasing its one-outstanding-phase barrier. A run-local pair marker binds the journal, own immutable charge projection and every individual phase file. It deliberately does not hash the entire changing owner database: other fully committed runs retain their charges without invalidating this run's clean pause.

Startup/resume independently reconstructs every own phase from current frozen assignments/plans and ledger evidence: request and payload, model/route, terms, seed/temperature/retries, quote, safe parsed answer/status, validity, charge, phase checkpoint bytes and exact receipt coverage. Foreign, duplicated or orphan own receipts, changed source/config/script, missing/replaced owner, interrupted phases, torn pairs and resealed semantic edits refuse before new calls. Global history is verified by the accepted ledger. Any unfinished global phase halts dispatch. A clean checkpoint permits resume after another fully completed run, without resetting charges. Concurrent attempts on one run are refused by its existing POSIX lock; callers must serialize different active runs against the one-global-phase barrier. This component does not promise concurrent-run throughput or automatic recovery.

## Invalid answers and failure boundaries

The visible raw/parsed answer remains in private accounting. Only exact built-in finite thermometer numbers in0–100 enter scoring. Other answers produce a null invalid-phase disposition rather than invented numbers; post is skipped when baseline is invalid. That scoring null is an invalid marker, not a synthetic respondent answer: the original malformed/missing/refused/oversized-number content remains privately retained. The evaluated post request for a skipped phase is a frozen hypothetical frame used for complete assignment validation; no post message or quote was dispatched. Invalid subtype counts and full-cohort attrition/scientific analysis still need separate live acceptance. Hosted-model/human effects cannot be inferred from this engineering analysis.

Exceptions/cancellation preserve global reservation/billing and a type-only sealed run failure; no automatic inference retry or refund occurs. Real child-process death is tested before POST, after settlement before journal completion, before owner phase commit and after owner commit before the run pair update. In the last case the old run refuses resume because its pair marker is stale, while another run may proceed: the prior billing, phase file and journal are already committed. That is not an unresolved global charge. Other tested interrupted global states block new runs as well as the old run.
