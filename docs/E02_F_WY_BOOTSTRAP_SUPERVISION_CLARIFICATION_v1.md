# E02 F Wyoming bootstrap supervision clarification v1

METHODS CLARIFICATION ONLY. Original bootstrap proposal and B06/B09 assertions remain immutable history. No new executable code, actual cache access or authority. This separate clarification limits the proposed implementation claims; it does not certify resource shutdown from conservative accounting.

## Finding and observed runtime topology

The original proposal's launcher-parent polling/process-group description is insufficient when that parent dies or a descendant changes session/group. A dead controlling parent cannot run its timeout handler. Killing one process group does not cover another session. An UNKNOWN ledger charge preserves accounting but says nothing about whether a process stopped.

Static inspection of pinned `national_population.py:supervise_fixture` shows its fork child explicitly calls `os.setsid()`. It samples worker RSS via `ps` and uses parent `finally` cleanup. Therefore the actual native runtime cannot be assumed to remain in an outer launcher's process group. Preserve this helper unchanged. Do not silently monkeypatch its process context, intercept os.setsid, claim process-tree polling removes races, or label native-parent finally cleanup an owner-death guarantee.

## Supported authored topology proposed for implementation

Use three distinct roles: requesting owner O, independent watchdog W, and a fixed cooperative stage C. W must already be running, outside O's process group/session and with its own lifetime before it accepts START. W owns the stage lifecycle and launches C; O never launches source-capable children directly. An isolated disposable authored fixture may create W as a detached independent process, but process survival/readiness must be observed and independently tested, not inferred merely from setsid. Production service installation/availability is NOT established here.

Before opening an authored input, W obtains the original journal lock, validates the pinned cooperative topology and budgets, records the reservation and earliest deadline, spawns C paused at a mandatory readiness barrier, and retains an OS process identity plus parentage/group/session/start identity. C reports its identity over a private fixed control channel. W confirms the allowed process/group and exact code and then acknowledges READY to O. Only after W's subsequent explicit GO may C access its input. C cannot spawn descendants, fork, setsid/setpgid, execute external programs or start alternative workers under this supported topology. Imported dependencies and entry points must be reviewed for that restriction. W is the only process launcher. Unexpected/unregistered processes or identities fail readiness; the stage receives no GO. Polling alone is not proof that arbitrary untrusted code cannot escape; cooperation of this exact pinned topology is an explicit trust assumption.

W monitors both O's OS identity/liveness and a dedicated owner-lifetime channel; a merely quiet channel is not proof of death. Only O holds the writing end; W/C close inherited copies before readiness. Owner death/lifetime EOF, broken readiness, cancellation or stale control state cancels further GO immediately. W terminates the exact registered C group/process, escalates to kill, verifies all supported registered stage identities have exited and reaps its child. W writes SHUTDOWN_CONFIRMED only with observed exit/reap evidence. If identities are ambiguous, killing is unsuccessful or shutdown cannot be observed, write SHUTDOWN_UNKNOWN when possible, retain full charges and block all further work. Do not report confirmed termination from signal delivery alone.

This addresses O dying while W survives, which is the bounded B06 scenario. W survives independently of O, continues checking the original deadlines and owns the work child. It does not promise enforcement if W is itself killed, the kernel/host fails or a trusted cooperative child violates the reviewed topology. On W loss or unprovable lifetime, owner/recovery logic refuses subsequent work and requires independent cleanup/liveness evidence; no automatic restart/retry/new journal/GO. Surviving work is possible in that unsupported failure, and conservative charging is not described as containment. No hostile-host sandbox or guarantee against arbitrary code is asserted.

## Unsupported actual runtime: refuse before work

The unchanged native helper's new-session multiprocessing child, plus its subprocess RSS checks, is outside the simple cooperative C topology. It does not implement the readiness/registration barrier needed above. Do not start it and then try to discover or kill escaped descendants. The future wrapper must identify this unsupported pinned topology from its validated backend/type/code contract before launching any source-capable native stage. It must refuse BEFORE actual cache stat/open/hash, before runtime admission/root creation and before ENROLL. No source inspector or runtime is launched to test compatibility on real bytes.

For this clarification the actual integration backend is explicitly UNAVAILABLE. A later independently reviewed containment/supervision backend or separately versioned compatible runtime design is required to support the original native topology, with owner-death/worker-readiness/descendant-lifetime tests. That is a remaining blocker, not permission to alter accepted runtime pins or lower the completion contract. Methods acceptance can authorize bounded authored implementation/tests only. Actual inspection and native execution remain gated even if those authored tests pass. A real production inspector also needs a reviewed supported topology and separate exact-source authorization.

## Timing, sampling and test interpretation

Earliest 10,800-second deadline, unchanged native caps, six-stage conservative reservations, per-stage 300 seconds and all failed/pending charges remain as previously specified. A surviving W uses the same t0 and preserved clock-continuity checks. Review/idle gaps count. The watchdog initiates cancellation at the earlier remaining global/stage deadline; a 0.1-second target sampling cadence is a check interval, not a maximum scheduling latency or absolute kernel CPU/wall/RSS cap. OS scheduling, blocking syscalls, ps sampling and termination/reaping can overrun; observed deadline/stop violations are recorded as failures with full charges, never clipped or certified within caps. If an absolute stop guarantee is required, this cooperative backend is unsupported and must refuse before work. Reserve/check cleanup/storage headroom, and record detection, signal, observed-exit and reap times separately.

B06 and B09 remain original assertions in the old proposal. Separate clarified acceptance cases are:

- S01: independent W readiness exists before GO; kill O after reserve/before GO and during cooperative C work. W remains alive, refuses new work, observes C termination/reap and preserves UNKNOWN/full charges as appropriate.
- S02: absent/dead/unready W, inherited owner-channel writer, ambiguous process identity or unregistered topology refuses before any authored source access.
- S03: request a child-spawning/setsid/native-helper backend. Refuse before launch/source access; do not simulate successful containment of an escaped child.
- S04: lose W or make exit evidence unavailable. Subsequent attempts remain blocked with SHUTDOWN_UNKNOWN; no claim that ledger charging terminated the old process. Test harness must own separate cleanup and disclose it.
- S05: expiry, clock rollback, delayed scheduling, RSS sample gaps and delayed termination preserve original t0/full charges and report measured overrun/unknown status honestly. No absolute time/RSS guarantee follows.
- S06: accepted source/runtime pins and original B06/B09 text remain unchanged; actual inspector/native backend is unavailable and refuses before actual source access or admission. Only explicitly authored cooperative topology is eligible for later implementation review.

All six are NOT RUN specifications. A methods decision precedes new executable code. Full native integration, live inspection, actual shutdown compatibility and production supervision remain BLOCKED. No K/S/E/I approvals, source identity, source continuation, fit/disclosure, GET/model calls, spend or publication authority is issued.
