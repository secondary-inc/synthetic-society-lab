# Idaho rendered-capture reader proposal v1.8

This is a methods/source-contract proposal for independent review. There is no new Idaho helper, fixture suite, runtime admission, recorded readiness run or coverage promotion. The batch06 source-role audit accepts bounded acquisition evidence; it does not accept a parser or legal ballot inference. All existing inputs, reports, readers and admission rules remain unchanged.

## Intended deliverable and source boundaries

Proposed standalone module: `src/civiclab/e01/idaho_v1_8.py`; proposed fixture suite: `tests/test_e01_idaho_v1_8.py`. Both remain unimplemented pending review. The helper would read only five pinned local artifacts: official November general-index HTTP body, official candidate-portal initial HTTP shell and three separately captured browser JSON representations. It would not perform GETs, browser interaction, hidden API calls, candidate-detail requests or filesystem writes. Standard-library JSON, HTML, date and hash handling should suffice.

The index's offered candidate link establishes source context. The portal HTTP shell is not the populated table. Browser captures contain rendered DOM/text with observation clocks and unavailable HTTP headers; they do not supply wire bytes, publisher update timestamps or independently immutable historical snapshots. Original files remain local and ignored, and their byte hashes are frozen in the companion proposal JSON. No raw redistribution permission is inferred.

The captured portal is selected to November03,2026 GENERAL and titled FINAL CANDIDATES LIST. The first representation shows50of592 rows; the Federal representation shows15of15; the Federal/United States Senator representation shows5of5. Party remains unfiltered. The later two capture arrays record Select All, Approved and Withdrawn checked. The first artifact lacks that checkbox array. It has both status values in its rows, but an exact checkbox-state assertion must remain unknown for that artifact. The historical live accessibility observation is separate from persisted checkbox evidence.

None of the three artifacts directly records the Candidate Name input's value. Matching five full Senator tuples and the selected pagination supports source-local reconciliation of the observed rows, not a claim that every possible name-filter state or current/upstream record has been enumerated. This gap is not repaired by reopening the website or rewriting raw captures in this task.

## Bounded parsing and reconciliation

Require exact JSON envelopes/keysets, observed URL and representation kind, UTC-aware chronological capture clocks, source hashes/sizes and unchanged bytes before/after parsing. Five exact regular nonsymlink paths only; reject ancestor symlinks/traversal. Proposed bounds are1MiB per artifact,5MiB total,750000 HTML characters,100000 DOM nodes, depth64 and exact50/15/5 data rows. Reject duplicate JSON keys/nonfinite numbers and malformed/duplicate/nested candidate tables.

Require one Smart Table with9 exact columns. The raw normalized header strings are BALLOT NAMEHeader, DISTRICT TYPEHeader, OFFICEHeader, DISTRICTHeader, PARTYHeader, DATE FILEDHeader, WRITE-INHeader, STATUSHeader and ACTIONS. Match the corresponding exact cdk-column identity tokens listed in the contract. Map only these observed header literals to their semantic names; do not delete arbitrary Header substrings from candidate/row text. Retain the original source artifacts instead of pretending normalized strings are wire-exact text.

Bind every captured filter, page-size/count/range, status checkbox and visible context value that actually exists. The initial no-office/no-status-array schema is a distinct reviewed variant, not an invitation to tolerate arbitrary missing fields. Require five unique full ballot-name strings in the exact Senate office block in every capture, with Federal district type and blank district. Mixed all/federal tables must have a next-office boundary at United States Representative and no later hidden extra Senate row. Compare all nine normalized cell tuples, including full names, literal party/status, filing date, district/write-in blanks and ACTIONS UI text, across all three captures in order. Compare full strings, not initial fragments or normalized major-party classes. Never activate View Details.

Dates remain exact source literals plus separately parsed ISO dates under `%m/%d/%Y`, not publication, certification or withdrawal dates. The five observed dates are in February2026 and precede the capture date. Preserve the four Approved records and one Withdrawn record. The withdrawn row's label is Democratic; Approved labels are Independent twice, Libertarian and Republican. Do not create an Approved Democratic row, infer a withdrawal date or collapse withdrawn history into active candidacies.

## Typed unknowns instead of forced ballot booleans

The existing ballot-roster schema is not adopted for this source. The standalone output would have record role `OBSERVED_GENERAL_CONTEXT_CANDIDACY_STATUS_HISTORY`, full local-only name, exact source office/type/party/status/date/district/write-in literals and all three capture/row locators. Approval is an observed portal status, not independent legal nomination.

Use explicit typed unknowns for write-in status, printed-ballot status, legal nomination and latest-amendment completeness. The write-in cells are blank; they do not establish a false Boolean. A final-titled general portal does not establish printed-ballot membership. Do not emit `printed_on_ballot`, `declared_write_in`, `legal_nominee` or inferred major-party candidate booleans. The companion JSON specifies field names, UNKNOWN reasons and forbidden inferred fields. Source status and party strings remain separate fields, with withdrawn history preserved.

A future integration would need a separately versioned status-observation/typed-unknown admission contract. It must not broaden the accepted base reader or retrofit unknowns into older state objects. If readiness cannot represent these records honestly, that integration gate remains blocked while the bounded standalone observations are retained. The original research requirement is not reduced to passing this source-local reader.

## Acceptance and negative fixtures

The first gate is independent review of this proposal. A second gate reviews exact standalone code, authored fixtures, runtime/path/hash guards, privacy and failure behavior. Only then may a separately approved actual-source helper preflight occur. Recorded readiness requires a later integration/schema review, authorization and independent post-run acceptance. No stage permits automatic coverage promotion, final ballot, geography, source-policy adoption or historical-cutoff claims.

Positive fixtures must use visibly authored DEMO names, exact captured structural variants, matching full tuples, blank cells and statuses. Test full tuple equality across all three representations, date-literal preservation, independent/Libertarian/Republican Approved labels, withdrawn Democratic history and typed UNKNOWN semantics. Actual-source checks must compare locally and emit only hashes/counts/context/party-status-date/blanks diagnostics. Real candidate/contact values stay in ignored local outputs; public reports, errors and bundles must refuse them.

The machine-readable contract enumerates negative criteria: wrong hash/path/import-approved contract identity; source mutation before/mid/after parse; duplicate JSON keys/keysets; wrong source/link/representation/date; malformed clocks; missing/reordered/duplicate tables/headers/rows; non-nine-cell rows; extra Senate rows/state-Senator contamination; filter/party/status/checkbox/pagination mismatches; name-fragment traps; tuple status/party/date/name edits; coordinated resealing against immutable approved source pins; invalid/future dates; nonblank district/write-in cells; unexpected action text; and unknown Boolean coercions. A reviewed runtime contract must be pinned to its independent acceptance receipt, not replaceable by caller-supplied coedited hashes. This proposal JSON is not that runtime release.

Keep deterministic public errors static and value-free. Pure standalone parsing returns only after all five inputs and rechecks succeed; an exception must not return partial candidates. Inject parser failures, KeyboardInterrupt and SystemExit at each input and after extraction before final result assembly. Any later persisted wrapper must retain its admitted failure with only exception type/static code, never raw values; it requires separate review and must not be added silently now. Preserve raw failed captures/configurations locally. No application tests are claimed executed for a module that does not yet exist.

AR general-source acquisition and GA access limitations remain separate unfinished jobs. No new GET/UI/API/model activity or experimental spend was required for this proposal.
